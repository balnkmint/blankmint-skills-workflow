# 状态与无上下文交接模板

复杂任务启动、阶段交付或暂停时按需填写。未知写“未确认”，不要补猜测。

## 目标与范围

- 用户要解决的问题：
- 已授权的修改范围：
- 本次不做的功能/既有缺陷：
- 当前决定（继续修复/保留现状待实测）：

|---|---|---|---|---|---|
| | | | | | |

说明本地与远端是否同版本、未提交改动、哪些测试旁路绝不能进正式版本。编号升级或同名重发要保留辨识信息。

## 故障与实现

1. 原始现象和复现命令。
2. 调用链、文件和函数定位；行号仅供定位，以当前源码为准。
3. 原逻辑、新逻辑、为何改变、接口/生命周期/并发差异。
4. 证实的根因及证据；尚未排除的解释单列。
5. 曾尝试但无效的方案及原因，防止重复试错。

## 验证边界

| 场景 | 环境/产物摘要 | 命令或日志位置 | 实际结果 | 结论 |
|---|---|---|---|---|
| | | | | 实测通过/用户反馈/推演/待验证 |

列出编译开关开/关、正常/异常、兼容性、性能和硬件依赖中实际覆盖了哪些。没有测试的项不写“无影响”。

## 下一步可直接执行的动作

- 先读的源码/补丁/文档的准确路径。
- 要核对的基线与配置。
- 最小诊断或修改步骤、预期结果与停止条件。
- 可选方案和取舍；明确“尚未实施”。
- 备份路径和限定范围的恢复办法；不使用宽泛删除或硬重置。
- 用户尚需决定的问题。

## 交付自查

- 新会话能否从路径定位实际文件，而非依赖“上面那个补丁”？
- 当前源代码、候选方案、用户反馈是否区分？
- 原提交信息、摘要和构建配置是否可追溯？
- 命令是否标明执行主机，失败时是否停止？
- 测试分支成果是否与正式分支/硬件验证分开描述？
