# 本地与离线服务器协作修改

## 工作边界

本地 AI 负责证据分析、最小修改、补丁校验和文档；用户通过获准渠道把文件传到堡垒机后的服务器，执行命令并回传结果。不得把本地操作描述为已在远端执行，不假设能 SSH，不要求离线服务器访问外网，不绕过传输审批或泄露代码。

用户只要求诊断时不改代码。要求修改时按本工作流推进；缺少关键源码先索取限定范围的证据，不凭历史对话猜补丁上下文。使用已有分支和构建方式，不擅自新建 worktree、切换构建体系或开启无关功能。

## 1. 建立环境与状态表

区分本地工作区、离线编译服务器、QEMU 宿主机、虚拟机和真实板卡；同一台机器可以承担多个角色，但路径、权限和产物必须明确。

最少确认：各角色源码路径、分支和 HEAD、未提交改动、目标架构、编译器、构建入口、实际配置和输出目录。按需确认 rootfs、动态库、工具链及传输限制。已有可靠信息不重复询问。

- `git status` 干净不代表本地副本与服务器一致；结合提交号、相关文件内容或摘要确认。
- `.config` 与受 Git 管理的配置片段不是一回事，切分支后配置及旧产物可能仍在。
- `uname` 不能证明用户态 GLIBC 版本；相同 CPU 架构不保证二进制兼容。
- 用户粘贴附件时读取正文，不把附件文件名或摘要当作完整日志。

首次复杂任务用 [交接模板](references/handoff.md) 建立记录；简单修复只填写必要项。

## 2. 从日志收敛到最小修改

每轮先给出：已确认结果、当前第一个实际阻塞、下一步动作及预期结果。区分源码事实、运行证据、推断和待验证项。

沿实际调用链检查调用方、被调用方及错误处理；迁移接口时核对目标版本声明、生命周期、并发和返回值语义。不要只把函数名替换到编译通过。按模块归并有依据的编译问题，不对已知未解决的问题反复全量构建。

保持用户指定的行为范围。既有缺陷与本次新增风险分别记录；不顺便扩展修复。应用层依赖“单次 read 返回完整帧”时，应检查应用缓存与组帧，不直接修改通用内核来维持不可靠假设。兼容性与性能只能给出依据及验证边界，不能保证绝对无影响。

## 3. 本地制作可追溯补丁

1. 阅读目标文件及局部依赖，确认本地基线与服务器提供的版本一致；不一致时先同步必要文件或精确上下文。
2. 保留用户已有改动。只修改任务范围内的文件，选择单一目的、便于回退的补丁粒度。
3. 从实际差异生成合法 unified diff 或 `git format-patch`，不手写缺少行号的 `@@`。未跟踪文件也必须明确纳入交付，不能误以为普通 `git diff` 会包含它们。
4. 记录编号、文件名、版本、SHA-256、基线、前置补丁、改动文件、目的及测试状态。改发同名补丁时明确“替换旧版”，更新摘要，避免用户应用旧文件。
5. 在匹配基线的可丢弃副本检查补丁并按任务做语法/编译检查；已有修改后的工作区不能用于证明正向可应用。反向检查只说明对应修改可能已存在，不替代基线验证。

不裁剪补丁的上下文空行或尾部空格来“美化”补丁；空格本身可能是 diff 上下文标记。不要混入二进制产物、密钥、运行日志或无关格式化。

## 4. 离线交付与执行

给用户一个明确的交付批次：文件位置和摘要、执行主机、工作目录、前置状态、命令、预期结果、失败后回传内容。按需使用 [命令模板](references/remote-commands.md)，替换占位符后才作为可执行步骤发出。

- 命令块使用干净 Bash，不带终端提示符、转义下划线或嵌套 Markdown；服务器、宿主机和虚拟机命令分块。
- 确认文件已传到对应目录后再应用。`git apply --check` 失败就停止；不要继续构建或打印误导性的 apply=0。
- `--ignore-space-change` / `--ignore-whitespace` 只用于证据明确的格式差异，不能作为所有失败的默认解决方案。不要自动使用 `--reject`、强制套补丁或覆盖源码。
- 检查失败时索取补丁摘要、当前 HEAD、相关差异、失败函数完整上下文；不能反复只调整行号猜版本。
- 离线依赖在允许联网的环境准备，核对来源、架构、版本和摘要，经批准渠道传入。不要向内网建议直接 apt/curl 下载。

## 5. 构建、部署与验证分层

配置生成、编译、链接、部署、运行测试逐级设门。构建管道立即捕获 make 的退出码；没有 CC 输出可能只是增量构建，无需仅因时间戳旧而强制重编译。记录产物摘要、版本和实际配置。

不要直接执行 `mrproper`、`git clean` 或 `reset --hard`。清理需求先说明范围并保留配置及必要产物。源码内构建与 `O=` 构建不要混用；失败后不要用另一个目录的旧配置继续充当本轮结果。

部署前确认目标没有被运行实例占用，备份原文件，验证候选产物与运行环境的兼容性，再替换。rootfs 镜像不能同时被 QEMU 和宿主机读写挂载。chroot 仅改变文件系统根，不更换内核；精简 rootfs 缺少编译工具时用兼容工具链/sysroot 或独立构建环境，不强行把编译器塞进产品镜像。

必须区分以下结论：

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 补丁检查及应用成功 | 当前源文件接受修改 | 功能正确 |
| Image/程序构建成功 | 当前配置下编译链接通过 | 未编译分支、运行兼容性 |
| QEMU 指定用例通过 | 该环境和路径的行为 | TEE、存储和板卡完整闭环 |
| 用户反馈某场景通过 | 用户报告的兼容结果 | 未提供证据的全量回归 |

涉及安全功能要覆盖正常/异常、开关配置、错误处理；涉及协议要覆盖拆包、粘包、长度边界和原有协议分支。用户暂不测试时记录剩余风险，不把静态推演标为实测。

## 6. 提交、正式分支与交接

用户授权后才提交或迁移。明确暂存文件，不用 `git add .` 混入构建产物。测试专用旁路、桩函数或无 TEE 模式与正式功能独立提交；按依赖顺序 cherry-pick 必要提交，不整分支合并测试旁路。记录原提交和新提交映射，不为了作者信息擅自重写历史。

正式分支再次核对配置和构建结果，不能只看分支名。更新用户指定的补丁清单、进度、测试文档或表格，保留原 commit 来源。只有必要文件变更，无需为了本 skill 自动建立整个文档体系。

结束时写清：已完成什么、证据是什么、未覆盖什么、用户下一步执行什么。暂停任务时用交接模板留下精确路径、基线、补丁、错误与待决策方案，使新 AI 无上下文也能恢复，不把未实施方案写成现状。
