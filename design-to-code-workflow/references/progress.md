# 实施条目与交接示例

在现有进度章节复制以下条目。设计正文存放稳定的行为约定，此处用编号引用。实际结果和历史证据留在条目下，下次开发从“下一步”接续。

~~~markdown
- [ ] 步骤编号 · 可独立验收的行为（详设 §…）
  - 依赖与实现位置：前置步骤、调用入口、处理函数、后端。
  - 实施及验收：做什么；在哪个环境执行哪项操作；观察什么才算通过。
  - 当前状态（日期）：未实现／部分实现／已实现，待验证／验证失败／已验证。纯验收步骤可写待执行。
  - 证据（日期）：条款或分支 → 代码位置 → 环境与命令或用例 → 预期与实际结果。
  - 缺口与下一步：缺哪一层或哪次验证；下一位开发者从哪里开始。
~~~

## 示例：配置写入后重启仍有效

设计约定：写入成功后重启读取新值；存储提交失败返回错误，读取仍为旧值。调用链如下。

~~~text
客户端 save → 服务端校验 → 存储后端 commit
                         ├─ 成功 → 发布新值 → 返回成功
                         └─ 失败 → 保留旧值 → 返回写入错误
~~~

以下为虚构示例，用于区分两种容易混写的进度。

- [x] 01 · 验证服务处理提交失败（示例详设 §3.2）
  - 验收环境为主机。用例 T01 使测试后端返回写入错误。
  - 实测：save 返回写入错误，随后 read 得到原值。此项验证服务逻辑。
- [ ] 02 · 验证正式配置后端的重启恢复（示例详设 §3.2）
  - 当前状态：部分实现。客户端和服务入口已接通，正式存储后端尚未接入。
  - 缺口与下一步：接通正式后端，在目标设备写入 B、确认成功、重启并读取，期望为 B。接线完成但尚未做此测试时，更新为“已实现，待目标设备验证”，仍保留空框。

若本轮只看到编译成功，证据写“目标构建通过”。若日志显示第一次读取成功、重启后读取失败，则在同一条目注明首次读取通过、重启恢复失败，并记录可复现的命令或用例。
