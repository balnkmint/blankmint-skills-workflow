# 从详设到实现与验证

用同一份 Markdown 回答三个问题：产品行为如何定义，开发者下一步要做什么，哪些行为已经在哪个环境验证过。优先维护用户指定的详设及其实施章节；项目已有独立进度文件时，在原处更新并引用详设条目。

## 接手时先判断本轮任务

- **写或改设计**：读用户最新决定、原始流程图、已有详设和相关代码。把图中的判断、失败返回、重试和退出条件逐个落实。标清现有实现、拟新增行为和待决定项。只设计时，交付文档即可。
- **按计划开发或“继续”**：先读进度章、目标步骤引用的正文与当前代码差异。找到用户指定步骤，或第一个依赖已具备的未勾选步骤。先核实上轮实际做到哪里，复用已有代码和证据。
- **复核或接收测试记录**：用实际构建、配置、环境和日志核对具体条目。记录失败落在哪一层，以及这次结果已经证明哪些前置步骤成功。用户自己编译或上板时，写出应执行的命令、预期结果和需要回传的最小证据。

## 把设计写到足以动手

1. 按组件和职责说明发起方、执行方、边界和数据归属。关键功能用短 ASCII 调用链写到现有函数或拟实现的函数；在判断点展开成功和失败两条分支。
2. 对每个对外入口明确调用条件、输入与输出方向、字段取值及含义、边界值、成功结果、错误和副作用。没有输入或输出的项目直接写“无”。共用编码在前文集中定义，具体接口引用并列出允许的组合。
3. 对有状态功能写清创建、查找、使用、释放，以及异常后的可见状态；涉及持久化时指出写入位置、何时算提交成功、重开或重启后能看到什么。只展开与需求相关的并发、权限或平台差异。
4. 为每个独立行为写一个从正常入口能观察的通过条件。用户修订某条设计时，同步检查调用图、字段表、实现清单和对应验收，避免旧设计继续指导开发。

## 把详设拆成 AI 可执行的清单

在详设末尾沿用现有编号建立分步清单。先让最小骨架通过一个真实入口往返，再按依赖补接口和共用资源，之后逐功能打通调用方、执行方及后端，最后做集成与目标环境验收。仅在确有依赖时规定先后顺序。占位实现需能辨认，尚未实现的业务调用返回明确的未支持或未就绪结果。

每步写明 **详设锚点、依赖、修改位置、工作内容、验收动作及通过条件**。步长以一次能够独立验证的行为为准。将只依赖主机的部分和必须上设备的部分拆开，使开发能在平台待就绪时继续。可直接采用[条目模板及示例](references/progress.md)。

## 实施一项，原地更新一项

1. **实施前**，逐项复核该步引用的参数表、流程和错误路径。把“源码有实现”“构建启用该实现”“运行产物实际使用该实现”分别判断。资料冲突时记录影响范围，继续可独立完成的部分。
2. **实施后**，从正常调用入口走一遍。按设计检查正常、边界、拒绝和失败路径，以及本步涉及的资源清理、状态变化和持久副作用。以实际调用方能观察到的行为作为断言，避免把内部偶然行为写成验收要求。
3. **回写 Markdown**，记录“正文条款 → 代码位置 → 环境及用例 → 预期与实测”。在原条目保留日期和证据。未运行的命令标为待执行；使用替身、模拟器或特定构建选项时写明其覆盖范围。复用已有用例编号或日志位置即可。
4. **打钩前**，逐一比对本步全部适用验收条件。缺实现写到具体函数、接口或后端；缺验证写到具体环境、操作和通过条件。只要还有一项未通过，保留未勾选。回归失败时重新打开原条目，保留历史通过记录并标明适用版本。
5. **结束本轮**，更新受影响的前置和下游条目，留下下一步可执行动作。完成整个计划前，双向核查“每条设计都有实现和验收去向，每个完成项都有证据”。发布、提交或推送依用户授权执行。
